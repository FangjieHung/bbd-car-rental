**日期：** 2026-09-23
**狀態：** 四批全部完成，在分支 `feat/admin-flow-review`（工作目錄 `.worktrees/admin-flow-review`），**尚未合併 `main`**

**相關文件：** 術語 `CONTEXT.md`、前一輪待辦 `docs/plans/2026-09-22-orders-page-frontend-todo.md`（本計畫取代其第 6 節）、業主 `docs/owner-questions.md`；完成後的細節見文末「完成紀錄」

## 審查結論（一句話）

後台有兩條建單路線、兩套選車方式：好的那條（先選日期、只列可租的車）藏在總覽搜尋卡後面，訂單列表的「新增」卻進到「全部車輛下拉」的建單頁；總覽的「＋新增訂單」點了沒反應。另有一個會掉資料的 bug：款項打了金額沒按「新增款項」，建立訂單時會被默默丟掉。

## 使用者已確認的決策（2026-09-23）

1. **建單入口合一**：拿掉總覽搜尋卡；任何「新增訂單」都進 `/orders/new`，第一步本身就是「先選租期 → 列出可租的車」。總覽右側「可用」分頁加還車日，點車直接進建單並帶入車與日期。
2. **訂單摘要欄**：放在建單頁左側、每一步都在；**拿掉第 5 步「確認建立」**（步驟變 4 步），它的待補清單移進摘要欄。
3. **時間軸**：搬到總覽，與月曆用「月曆｜時間軸」切換、共用右側面板；車輛清單只留表格。
4. **待整備**：做成**不擋交車**的待辦清單（還車後自動列入、按「整備完成」移除；不改車輛狀態、不影響可用數，同一天又要交車時提醒）。
5. **執行方式**：四批依序做，每批跑測試、實機截圖對照後回報。

## 共同規範（每一批都適用）

- **文案**一律放 `apps/admin/src/app/core/i18n/zh-tw.ts`（`ZH_TW`），模板不寫死中文。名詞依 `CONTEXT.md`（訂單、據點、需調度、承租人、駕駛人…）。
- **顏色／圓角／陰影**只用既有 token（`--mat-sys-*`、`--app-*`）與既有元件（狀態 chip 沿用 `shared/chips` 與 `STATUS_TONE`），不寫死色碼；Midnight 深色配色也要能看。
- **元件放置**：新放進 `libs/ui` 的元件 selector 用 `lib-` 前綴（lint 規則）；admin 元件用 `app-`。
- **架構鐵律**（沿用）：元件只經 Signal store；store 只依賴 `Repository<T>`；車輛狀態只經 `VehicleStore.transition()`。
- **測試**：新行為要有 vitest 測試；修 bug 先寫會失敗的測試。
- **不改官網行為**：動到 `libs/booking-flow`／`libs/ui` 時，`booking`、`affiliate`、`booking-flow` 的測試要全過。
- **環境**：Node 24（`export PATH=~/.nvm/versions/node/v24.18.0/bin:$PATH`）、`NX_DAEMON=false`。驗收用的 build 一律 `--output-path` 到 repo 外；**不要**另開 `ng serve`（這台機器記憶體很緊）。

## 批次 1：會算錯或會誤導的先修

### 1.1 收款改成「列表就是紀錄」（修：輸入金額沒按新增款項會被丟掉）

- **現況**：`order-payment-drafts-section` 有一列獨立的輸入列＋「＋ 新增款項」；送出只讀已加入的清單（`admin-order-submit.gateway.ts:112`），輸入列上的值被默默丟掉，沒有任何提示或測試。
- **目標行為**：
  - 區塊標題「本次收款」。沒有任何一筆時顯示「尚未收款。建立訂單後，也可以在訂單的款項分頁收款。」
  - 文字按鈕「＋ 新增一筆收款」新增一列。第一筆預設「用途＝訂金、金額＝應收訂金（扣掉已列入的訂金）」，之後預設「用途＝尾款、金額空白」；方式預設現金。
  - 每一列：用途（下拉）、方式（下拉）、金額（數字）、刪除圖示按鈕（無障礙名稱「刪除這筆收款」）。**列上看到的值就是會記錄的值**，可以直接改。
  - 金額必填且大於 0；不合格時欄位顯示錯誤，並列入送出時的問題（掛在「費用與付款」步驟）。
  - 區塊底部一行：「本次收款 NT$X · 建立後待收 NT$Y」，Y＝報價合計−X；Y 小於 0 時改為「溢收 NT$Z」並用警示色。
  - 上方「訂金」欄位改名「**應收訂金**」，說明寫出上限與由來（依 `libs/domain/src/lib/pricing/deposit-cap.ts` 的實際規則，例如「上限 NT$3,164（報價合計的 30%）」；規則上限為 0 的車種要寫出正確說法）。
- **驗收**：重現原 bug 的測試（改前失敗、改後通過）；新增／刪除／修改列、合計、待收、溢收、金額驗證都有測試；訂單詳情的「編輯」不受影響。

### 1.2 月曆格與右側面板的取／還數字統一

- **現況**：`dayStats()`（`features/dispatch/calendar-view/calendar-view.component.ts:114`）只算預訂＋出租中；面板的取車算預訂＋出租中＋已完成、還車只算出租中＋已完成（同檔 :141-158）。實例：9/23 月曆「取 2 還 1」、面板「取車 0/2 · 還車 0/0」；未來日期的還車分頁看不到尚未取車的預訂，過去日期的月曆格看不到已完成的取還。
- **目標**：一個共用定義，月曆格與面板都用它。
  - 計入：會佔用車輛的有效訂單（沿用 `libs/domain` 的狀態定義）＋已完成；排除已取消與尚未成立者。
  - **取車（某日）**＝取車時間在那天；已完成＝已取車。
  - **還車（某日）**＝還車時間在那天；已完成＝已還車。**尚未取車的預訂也列入那天的還車清單**，標「尚未取車」，不提供「辦理還車」。
  - **今天**的還車清單另外列出「逾時未還」（出租中且還車時間已過）的訂單，排最前面並標出逾時多久。月曆格的還車數不計逾時。
  - 月曆格的「取 N／還 N」＝同一天面板的總數；過去的日子也照算。
- **驗收**：單元測試涵蓋上述四種情況；以種子資料抽查 9/23、9/25，月曆數字＝面板總數。

### 1.3 月曆「可用 N」與可用清單用同一個判斷

- **現況**：月曆的可用＝總車數−當天佔用，沒扣保養中（JKL-012）；可用清單用 `isVehicleAvailable`（有扣）。
- **目標**：月曆可用數＝那一天用同一個判斷算出的可租車數。
- **驗收**：測試（保養中的車不計入）；種子資料同一天月曆可用數＝可用清單筆數。

### 1.4 總覽頁首按鈕與放大鏡

- 「＋ 新增訂單」→ `/orders/new`。
- 「待保養 N」→ `/vehicles?maintenance=due`；車輛清單讀這個參數，只顯示有保養警示（逾期或即將到期）的車，並顯示可移除的篩選標籤「只看待保養」。
- 放大鏡：送出後導到 `/bookings?q=關鍵字`；訂單列表讀 `q` 預填搜尋；訂單列表搜尋除姓名、車牌外也比對**電話**（比對前去掉空白與連字號）。
- 「待整備」本批不動（批次 4）。
- 頁首按鈕文字改用 `ZH_TW`（`zh-tw.ts` 內有一段沒人用的 `dashboard` 字串可整理重用）。
- **驗收**：導頁與參數的測試。

### 1.5 車輛表單清空欄位存不進去

- **現況**：`features/vehicles/dialogs/vehicle-form-dialog.component.ts:71-74` 空值時省略欄位，repo 是淺合併，舊值保留（所在據點、排氣量、下次保養里程、保險到期日）。
- **目標**：清空＝真的清掉；`VehicleStore.create/update` 的型別補上 `location`。
- **驗收**：測試：已有據點的車改成「未指定」存檔後讀回沒有據點；另外三個欄位同。

### 1.6 訂單詳情的標題狀態與收款狀態

- 標題旁除主狀態外，顯示與訂單列表**同一套**急迫狀態（逾時未還、退款待處理等），共用判斷、不重寫。
- 總覽分頁「費用」卡加上「已收」「待收」（與款項分頁同一套計算）；沒有報價快照時仍顯示已收。
- **驗收**：測試；種子訂單 b9（MNO-345・林美惠，出租中＋逾時未還、已收 700）抽查。

### 1.7 交還車分頁

- 所有時間改用共用的日期時間格式（本地時區），不可露出 ISO 字串（`2026-09-20T01:00` 其實是 UTC，本地是 09:00）。
- 還車表單：里程欄提示「取車時 {n} km」並驗證不可小於取車里程；能源讀數欄提示取車時的讀數。**不預填**（避免沒實際查看就送出）。
- **驗收**：測試；b9 抽查。

### 1.8 全站金額、里程、日期格式（1.1–1.7 合併後才做）

- **金額**：共用格式化 →「NT$10,545」，負數「−NT$700」。純函式放 `libs/domain`（官網日後可用），admin 提供 pipe；套用到 admin 所有金額顯示（建單各區塊、訂單詳情各分頁、總覽面板、定價、優惠券固定金額、配件單價、通路固定退佣、退佣報表、保養費用…）。輸入欄位維持純數字。
- **里程**：千分位；單位寫在欄名「里程（km）」。
- **表格數字欄**：靠右、等寬數字（`font-variant-numeric: tabular-nums`）；`lib-data-table` 若支援欄位對齊就用設定，否則加共用 class。
- **日期**：`fmtDate` →「YYYY/MM/DD」；`fmtDateTime` → 當年「MM/DD HH:mm」、跨年「YYYY/MM/DD HH:mm」。取代 admin 內所有「YYYY-MM-DD」與 ISO 字串切片的顯示。
- **通路管理**「退佣方式」補單位：「10%」「每車每日 NT$100」。
- **驗收**：格式化函式測試（0、負數、大數、跨年）；admin 模板中找不到金額的裸插值（例外逐條說明）。

## 批次 2：建單頁重組

### 2.1 全站頁首標題

- **規則**：麵包屑＝上層路徑（可點）；大標題＝這一頁的名字，是頁面唯一的 `h1`。側欄品牌不再是 `h1`。
- 提供讓頁面設定標題與麵包屑的方式，並允許在標題旁放頁面自訂內容（訂單詳情的狀態 chip）。
- 套用：`/orders/new`：訂單管理 › **新增訂單**（移除頁內自己的標題）；`/orders/:id`：訂單管理 › **{承租人姓名}**，狀態 chip 在標題旁，頁內卡片移除姓名、保留車輛與租期，「← 返回」併入麵包屑；`/bookings/members`：訂單管理 › **會員**；`/vehicles/:id`：商品管理 › 車輛清單 › **{車牌}**；`/settings`：**設定**（現在錯顯「總覽」）。其他頁維持「群組 › 頁名」。
- **驗收**：header 測試；逐頁確認只有一個 `h1`、麵包屑可點。

### 2.2 建單頁版面框架

- 卡片撐滿主內容區的可視高度：上方步驟列、中間內容區自己捲動、**底部操作列固定在卡片底**。視窗太矮（約 600px 以下）或手機寬度時退回自然排版，操作列改 sticky。
- **左側「訂單摘要」欄**（桌機 ≥ 1280px 並排、寬約 280px；以下收成卡片頂端一條可展開的摘要列）：
  - 車輛（車牌＋車款）、取車／還車時間、天數、取車／還車據點（需調度時顯示路線）、承租人（姓名、電話）、保險方案
  - 租金、保險、配件、報價合計、應收訂金、本次收款、建立後待收
  - 「建立訂單需要」：車輛、租期、承租人逐項打勾（`CONTEXT.md` 的「訂單底線」）
  - 「建立後待補」：原第 5 步的 `orderIncompleteItems()`
- **拿掉第 5 步**：步驟＝租期與車輛／承租人與駕駛資格／費用與付款／合約。
- **操作列**：左「取消」（文字按鈕）；右依序：缺項提示（「還缺：承租人」，齊了就不顯示）、「上一步」（第一步不顯示）、「下一步」（最後一步不顯示）、「建立訂單」（唯一實心主按鈕，每一步都可按——維持既有設計）。
- **錯誤**：保留欄位錯誤與步驟標題錯誤；底部紅框清單改成一行「還有 N 項待修正」，點了跳到第一個有問題的步驟。
- 拿掉 880px 寬度上限。
- **驗收**：四步切換時操作列位置不變（1920×1080 與 1366×768 量 `getBoundingClientRect().top`，差距 ≤ 1px 且在視窗內）；步驟數與錯誤顯示的測試更新。

### 2.3 第 1 步：先選租期，再列可租的車

- **搜尋列**：車型、租期（共用的雙月日期區間選擇器）、取車時間、還車時間（30 分鐘一格，預設 09:00）、取車據點、還車據點（預設同取車據點）。選完即時更新，不需要搜尋鈕。
- **可租清單**（admin 元件，批次 3 的總覽可用分頁共用）：
  - 只列整段期間可租的車（與 1.3 同一判斷），依車型篩選。
  - 排序：已在取車據點的車排前面，其餘依據點、車牌。
  - 每列：單選、車牌＋車款、「在 {所在據點}」、「免調度」或「需調度 {所在據點}→{取車據點}」、這段期間的租金（定價引擎）。整列可點。
  - 同車型但不能租的車收在下方「另有 N 台這段期間不能租」，展開寫原因（已預訂 {起訖}／保養中）。
  - 整段都沒車：「這段期間沒有可租的{車型}」＋不能租清單（預設展開）。
- 從網址帶入 `vehicleId`／`start`／`end` 時預填並預選；該車不能租時提示「原本選的 {車牌} 這段期間不能租」。
- **共用元件**：雙月日期區間選擇器從 `libs/booking-flow` 搬到 `libs/ui`（標籤改注入 token、selector 改 `lib-`），官網改從 `libs/ui` 引用、行為不變。牽動超出預期就保留原位，並在回報說明。
- **驗收**：測試（可租判斷、排序、需調度、預填、不能租提示）；`booking-flow`／`booking`／`affiliate` 測試全過。

### 2.4 第 3 步表格化

- 保險方案：表格式單選（不加保＋各級方案）｜事故自負額｜每日｜{天數} 天小計。
- 加購配件：項目｜單價（/日 或 /次）｜數量步進器（− n +，不小於 0）｜小計，最後一列配件小計。
- 移除步驟頂端的唯讀金額清單（已在摘要欄）；1.1 的應收訂金與本次收款接在下方。
- **驗收**：測試（步進、小計、保險對報價的影響）。

## 批次 3：總覽與調度

### 3.1 拿掉總覽搜尋卡，月曆卡片上移

### 3.2 右側「可用」分頁

- 上方：起租日（＝月曆選取日）、「還車日」（預設隔天、不可早於起租日）、車型篩選。
- 清單共用 2.3 的可租清單元件（不需單選）；**整列點擊 → `/orders/new?vehicleId&start&end`**（時間預設 09:00）。
- 分頁標籤數字＝這段期間可租車數。移除官網車款卡（「或同級」「立即確認」等官網用語）。

### 3.3 月曆格

- 新增「需調度 N」（N>0 才顯示、警示色），判斷與取車分頁的需調度相同。
- 「可用 N」降噪：一般為淡色純文字；可用數 ≤ 1 時轉醒目；過去的日子不顯示可用。

### 3.4 右側面板細節

- 分頁標籤統一為「取車 2」＋細字「已完成 0」（可用分頁只有數字）。
- 需調度 chip 寫出路線「需調度 {所在據點}→{取車據點}」。
- 換月不關閉面板：原選取日不在新月份時，改選該月 1 日（新月份含今天則選今天）。

### 3.5 時間軸搬到總覽

- 月曆卡片標題列加「月曆｜時間軸」切換（`zh-tw.ts` 已有未使用的 `dispatch.calendar`／`dispatch.timeline` 字串），兩種檢視共用右側面板；時間軸上點日期欄＝選取那天；「今天」按鈕兩種檢視都有效。
- 範圍：選取日所在週的週日起 14 天，左右切換 ±7 天。
- 每列＝一台車：列首顯示車牌、車款、所在據點；色塊顯示承租人與取車據點；需調度的訂單在色塊起點加標記；**逾時未還的色塊延伸到今天並用警示色**（現在逾時的租約在時間軸上看不出來）；保養中的車整列標示。點色塊開訂單詳情。
- 車輛清單頁移除「表格／時間軸」切換，只留表格。

### 與原規格不同的決定

執行過程中，以下幾點跟原始規格文字（本文件批次 1–4 的敘述）字面上不完全一致，都經過
確認、屬於刻意的實作判斷，不是遺漏：

1. **摘要欄的實際版面**：不是「整張卡片左側一欄」，而是卡片**上半部**左側一欄、與步驟
   內容並排（CSS Grid `'summary main'`）；操作列在卡片**下半部**，橫跨摘要欄與步驟內容
   兩欄的寬度（`'footer footer'`），不侷限在步驟內容那一欄。見
   `apps/admin/src/app/features/orders/pages/order-create-page.component.scss` 的
   `$summary-docked` 媒體查詢。
2. **還車日的下限比字面規格嚴格**：規格寫「預設隔天、不可早於起租日」，讀起來像「同一天
   也可以選、只是預設隔天」；實作是**同一天完全不能選**——原生日期欄位的 `min`、預設值、
   手動輸入的下限三處都鎖在「起租隔天」，因為取還車都固定 09:00，同一天還車等於租期是
   零。見 `apps/admin/src/app/features/dispatch/calendar-view/calendar-view.component.ts`
   的 `minReturnDateKey`。
3. **「建立訂單需要」實際是 4 項，不是 3 項**：`CONTEXT.md`「訂單底線」定義車輛、租期、
   承租人三者齊備即可建立訂單，摘要欄的檢查清單卻多了「據點」一項（取車與還車據點都要
   選）。這是實作時發現的必要條件，據點沒選就無法算出報價與是否需調度，因此保留在
   `order-form-derived.ts` 的 `orderRequirements()` 裡，未回頭精簡成 3 項；`CONTEXT.md`
   的定義本身沒有跟著改，這裡先記錄，是否要更新定義待之後判斷。
4. **待整備同車重複還車，舊筆用「取代」而非「完成」處理**：同一台車還沒整備完又辦了一次
   還車時，舊的那筆 `PrepTask` 被標記 `supersededBy`（指向新那筆）而不是 `completedAt`——
   刻意保留「這次沒整備就出車」的紀錄，待整備清單裡這台車仍然只顯示最新那一筆。
5. **待補清單裡「會員未提供 Email」「證件未查核」「駕駛資格未查核」三項不會跳分頁**：
   這三項屬於會員資料、不是訂單本身的欄位（訂單的「編輯」不含它們，文件分頁也還沒做），
   點了改成直接開承租人的會員資料視窗，其餘（款項、合約）項目才跳對應分頁。
6. **順手修掉一個既有 bug：證件版本原本永遠寫死 `version: 1`**：不算這次規格內的項目，
   但影響 4.2 能不能正確運作——改之前每次上傳身分證件或駕照都固定存成第 1 版，交車檢查
   「取最新版本」的邏輯因此一直拿到最舊那筆，客人換發新駕照後現場再核對也看不出更新。
   現在新版本 `version` 遞增、`supersededId` 指回前一版（見
   `apps/admin/src/app/stores/document/document.store.ts`）。
7. **1.3「可用判斷」實際呼叫的函式名稱跟規格不同**：規格與批次 1 原始 commit 都寫
   `isVehicleAvailable`，但那個函式現在只服務官網／代訂站的單車單日判斷；admin 的月曆、
   可租清單、總覽可用分頁改呼叫同目錄下、後來新增的 `vehicleAvailability()` /
   `vehicleUnavailableReasons()`（能一次問一批車、還能附「為什麼不能租」的原因）。兩者
   底層邏輯一致（`isVehicleAvailable` 內部就是委派給 `vehicleUnavailableReasons()`），只是
   admin 端呼叫的具體函式名稱換了，寫文件／查代碼時要注意別找錯函式。
8. **1.8 的日期格式化函式沒有搬進 `libs/domain`**：只有 `formatTwd()`（金額）依規格放進
   `libs/domain/src/lib/formatting/`；`fmtDate`／`fmtDateTime`／`fmtIsoDate` 仍是 admin
   本地的 `apps/admin/src/app/core/date-utils.ts`，官網目前沒有共用日期格式化的需求，先
   不跟著搬。
9. **880px 寬度上限拿掉後，又在 2.2 polish 加回一個更窄的 960px 上限**：範圍縮小了——只
   限步驟內容區（第 3 步表格較寬，避免拉到跟卡片一樣寬），靠左對齊、不置中，摘要欄與
   底部操作列不受影響。規格文字「拿掉 880px 寬度上限」本身沒錯，只是後續 acceptance
   pass 又加了一個性質不同、範圍更小的上限，這裡一併記錄。
