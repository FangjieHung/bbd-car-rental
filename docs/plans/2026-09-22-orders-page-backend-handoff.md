# 訂單頁面化與據點統一：後端 Hand-off

**日期：** 2026-09-22
**上游：** `docs/plans/2026-09-18-rental-operations-backend-handoff.md`（通用原則、身分權限、證件、OCR、付款、合約證據等，本文不重複）
**術語：** 以 repo 根目錄 `CONTEXT.md` 為準
**待業主確認：** `docs/owner-questions.md`（本文多處依賴其中答案，標示為「待業主 #n」）
**目的：** 記錄這次前端改動對後端提出的新需求與新約定——建立訂單改為頁面、合約「先簽後建」、據點成為主檔、需調度的判定方式。

## 1. 建立與編輯訂單

### 1.1 前端期待的介面

前端把送出寫成一個可替換的 gateway（`apps/admin/src/app/features/orders/order-form/order-submit-gateway.ts`），目前由 admin 的本機 stores 實作。後端接上時實作同一個介面即可：

```text
OrderSubmitGateway
  create(input)            → 新訂單 id
  update(orderId, input)   → 訂單 id

input = { value: 表單值, presignature?: { assetId, snapshot } }
```

失敗時以帶錯誤碼的例外回報；前端不解析錯誤訊息文字。

### 1.2 伺服器必須自行驗證

前端的檢查只為即時回饋，**後端必須重做一次**：

- **訂單底線**：客人、車輛、租期三者齊備，且還車時間晚於取車時間。其餘欄位允許空白，建立後以「待補項目」呈現（見第 5 節）。
- **完整性規則**：車輛時段衝突（編輯時排除自己）、取／還車據點必填且為有效據點、保險方案必須可對帳、訂金不得超過上限。
- 不要信任前端送來的金額；報價由後端依定價規則重算。

### 1.3 原子性

目前前端依序執行「解析或建立會員 → 建立／更新訂單 → 登記款項 → 產生合約版本 →（有預簽時）簽署 → 排程提醒」，任一步失敗時由前端逐步回滾。**這在真實環境不可靠**（網路中斷會留下半套資料）。後端需把整段包成一個交易或具補償機制的 saga，前端只呼叫一次。

## 2. 合約：先簽後建

### 2.1 新流程

櫃檯建單時，客人在第四步簽的是「以目前表單內容產生的預覽合約」——**此時訂單與合約版本都還不存在**。前端暫存簽名資產 id 與簽署當下的合約快照，送出時一併帶上（`presignature`）。

後端建立訂單時：

1. 由訂單資料產生正式合約快照。
2. 若有 `presignature`，比對其快照與正式快照的**條款內容**（排除 id、時間戳等每次都不同的欄位）；一致才將簽名套用到新版本並標記為已簽署，不一致則忽略簽名、合約維持未簽署。
3. 比對必須在伺服器端進行，不能接受前端傳來的「條款一致」旗標。

前端比對規則可參考 `order-form/contract-snapshot.ts` 的 `sameContractTerms`，但後端應以自己的正規化方式為準。

### 2.2 需重新簽署

- 定義：客人簽過較早版本，但目前有效版本（最新且未被取代）尚未簽署。對交車而言等同未簽署。
- 前端判定集中在 `libs/domain/src/lib/contracts/contract-signing-state.ts`，交車就緒檢查已改用同一規則。
- 後端的交車檢查必須以「目前有效版本是否已簽署」為準（與上游文件第 15 節第 10 條一致）。

### 2.3 官網訂單的合約產生時機（待業主 #3，已有暫定決定）

官網下單目前**不會產生合約版本**，因此客人無法在自己手機上簽約。合約應在哪個時點產生需業主決定；決定後後端需在該時點建立第一版草稿。

### 2.4 客人在自己手機上簽署（待業主 #3、#4）

共用簽署元件已抽成 `libs/contract-signing`，同一個畫面可用於櫃檯簽名裝置與客人手機。要讓官網客人自行簽署，後端需要：

- 產生**綁定特定合約版本**的簽署連結：一次性、短效、可撤銷。
- 開啟連結時驗證身分（方式待業主 #4）。
- 若連結開啟後合約已產生新版本，連結失效並提示需重新簽署。
- 簽署證據欄位沿用上游文件第 11 節。**承租人與駕駛人不同人時誰要簽**，待業主 #4。

## 3. 據點主檔

### 3.1 資料

目前據點是前端常數 `RENTAL_BRANCHES`（`libs/domain/src/lib/models/branch.ts`），四筆為虛構示範資料（待業主 #7）。需要成為資料表：

| 欄位 | 說明 |
|---|---|
| `id` | 穩定識別碼，例如 `mzg-airport` |
| `name` | 顯示名稱 |
| `type` | 據點類型：`airport` / `port` / `store`（分類，不是地點） |
| `address` | 地址 |
| 營業時間 | 是否限制可選取／還車時段，待業主 #7 |

### 3.2 引用關係

- `Vehicle.location`（車輛所在據點）、`RentalBooking.pickupLocation` / `returnLocation`（取／還車據點）**現在存的都是據點 id**。欄位名稱是歷史遺留，前端之後會更名（見前端待辦），API 設計時建議直接用 `pickupBranchId` 這類名稱。
- **合約快照存據點名稱文字**，不存 id——快照是不可變的人類可讀文件，據點日後改名不應回頭改動已簽的合約。

### 3.3 舊資料遷移

使用者瀏覽器與早期資料中存在舊值，前端讀取時已自動遷移，後端匯入時請套用同一份對照：

| 舊值 | 新據點 id |
|---|---|
| `機場` | `mzg-airport` |
| `港口` | `mzg-port` |
| `店舖` | `mzg-store` |
| `馬公門市` | `mzg-store` |

查無對應的值原樣保留，不要猜測。

### 3.4 保險方案

目前保險方案是前端依**車輛分類**提供的示範常數（`libs/domain/src/lib/models/insurance-catalog.ts`），車輛資料上的 `insurancePlans` 由分類帶入，不是逐車設定。實際商品內容與費率待業主提供（待業主 #10）。

後端接手時建議：

- 方案是**主檔**，不要嵌在車輛資料裡；以車輛分類（或特定車輛）對應方案，並帶生效期間，改價不影響已成立的訂單。
- 訂單只存 `insurancePlanId` 與當下算出的 `insuranceSubtotal`；合約快照存方案名稱與保障內容的文字，日後改名或改價都不影響已簽的合約。
- 若是外購保單，需要保單號碼、保險公司、理賠窗口等欄位，並釐清退訂時保費是否可退（與取消規則交互作用）。

## 4. 需調度

- 定義：訂單為 `reserved`，且取車據點與車輛所在據點不同、兩者皆為有效據點。
- **這是衍生值，不存任何欄位**。任何一邊改變，判定立即跟著變；存成欄位會在有人改了據點卻沒同步時變成錯的資料。
- 前端判定：`libs/domain` 的 `needsDispatch()`。後端若提供查詢，請以同一條規則即時計算。
- 若日後要把調度變成有負責人、有時限的工作（待業主 #2），請建成**獨立的調度任務實體**引用訂單，而不是在訂單上加旗標。
- 還車到不同據點後車輛所在據點是否自動更新（待業主 #1）：**暫定決定為「是」**（2026-09-23，待業主會議確認）——還車手續完成時把車輛所在據點更新為還車據點，不另外產生「調回原據點」的工作。**前端已實作**（`apps/admin/src/app/stores/handover/handover.store.ts` 的 `performReturn()`：車輛狀態轉為 available 之後，另外把所在據點寫成該筆訂單的 `returnLocation`，兩者是分開的欄位更新，所在據點不經狀態機）；後端接手時請把這個更新放在還車完成的同一個交易裡。

## 5. 訂單狀態與待補項目

- 訂單狀態只有四個：`reserved`、`in_progress`、`completed`、`cancelled`。**沒有草稿狀態**，這是刻意的決定（新增狀態會牽動可用性計算：草稿到底佔不佔車？）。
- 付款狀態由款項紀錄獨立追蹤，不是訂單狀態的一部分。
- 「待補項目」（未收訂金、合約未簽、證件未查核等）是**由其他紀錄衍生**的清單，不是訂單上的欄位。前端邏輯已搬到 `features/orders/incomplete/order-incomplete.ts` 的 `orderIncompleteItems()`（2026-09-24 更正：原本在 `order-form/order-form-derived.ts` 的同名函式已搬走；那個檔案現在只剩 `orderFormProblems()`／`orderRequirements()` 這類「建立訂單需要」的表單驗證，是另一套清單，別搞混）。詳見第 9.3 節。
- 注意：`docs/architecture/02-libs.md` 描述的舊狀態機（`pending_payment` → `confirmed` → …）已過時，以 `libs/domain/src/lib/models/enums.ts` 為準。

## 6. 付款方式的兩套列舉

系統目前有兩個不同的付款列舉，交集不完全：

| 列舉 | 用途 | 值 |
|---|---|---|
| `PaymentPreference` | 官網客人下單時選的偏好 | `credit_card`、`line_pay`、`on_site`、`bank_transfer` |
| `PaymentMethod` | 櫃檯實際收款方式 | `cash`、`credit_card`、`line_pay`、`bank_transfer`、`customer_credit` |

兩者的選項與預設標籤已集中到 `libs/domain`（`PAYMENT_PREFERENCE_OPTIONS`、`PAYMENT_METHOD_OPTIONS`）。後端需定義 `on_site` 對應到哪些實收方式，以及 `customer_credit`（保留金折抵）只能由櫃檯使用的限制。

## 7. 後端驗收情境（補充上游第 15 節）

1. 只有客人、車輛、租期的訂單可以建立，並回傳正確的待補項目。
2. 還車時間早於取車時間的建立請求被拒絕，錯誤碼可供前端對應欄位。
3. 建立訂單中途失敗不會留下孤兒會員、款項或合約版本。
4. 帶預簽名建立、條款與簽署當下一致 → 合約為已簽署；條款不一致 → 簽名被忽略、合約未簽署。
5. 已簽署訂單修改租期後，交車檢查回報合約未簽署（需重新簽署）。
6. 車輛所在據點或取車據點任一改變，需調度判定即時反映。
7. 以舊值（`馬公門市` 等）匯入的資料全部對應到有效據點 id。
8. 簽署連結在合約改版後失效。

## 8. 整備待辦（2026-09-24 追加，後台流程審查 4.3）

「整備」＝還車之後、下一次交車之前的清潔與檢查（`CONTEXT.md`「整備」）。**暫定為不擋交車的待辦清單**（待業主 #11）：不改車輛狀態、不影響可用數、不擋取車，只在這台車還沒整備就又要交車時提醒。前端模型 `libs/domain/src/lib/models/prep-task.ts`，排序規則 `libs/domain/src/lib/prep/prep-queue.ts`。

### 8.1 資料

| 欄位 | 說明 |
|---|---|
| `id` | 識別碼 |
| `vehicleId` | 車輛 |
| `bookingId` | 觸發這筆整備的訂單（剛辦完還車的那一筆）；一筆還車只會有一筆整備 |
| `returnedAt` | 實際還車時間（還車紀錄的實際時間，不是訂單約定的還車時間） |
| `returnLocation` | 還車據點 id（該筆訂單的還車據點） |
| `completedAt` / `completedBy` | 按「整備完成」的時間與操作人；未完成為空。操作人請取自登入身分（前端目前沒有登入，暫以後台使用者名稱代替） |
| `supersededBy` | 還沒整備就又還車一次時，舊的那筆被新的取代（值為新那筆的 id）；**取代不是完成**，完成欄位維持空白，保留「沒整備就出車」的紀錄 |

「未完成」＝`completedAt` 與 `supersededBy` 都是空的。同一台車任何時候最多一筆未完成。

### 8.2 產生與結案

- **產生**：還車完成時由伺服器建立，請放在還車完成的**同一個交易**裡（與車輛狀態轉換、所在據點更新同一批，見第 4 節）。前端目前把它當成還車協調流程的一個步驟（`HandoverStore.performReturn()` 的 `prep_task_create`，失敗時走既有的部分失敗回報），接上後端就不需要前端自己建。同一台車若還有未完成的整備，同時把舊的標記為被取代。
- **結案**：「整備完成」只記錄時間與操作人，不刪資料。已結案的再按一次不得改寫第一次的紀錄。
- **不得連動**：整備**不改**車輛狀態、**不列入**可用數與可租清單的計算、**不列入**取車就緒判斷的阻擋項目。若業主 #11 改成「要擋」，這幾條都要重新設計，不要只在前端加判斷。

### 8.3 前端期待的介面

```text
GET  /prep-tasks?status=open         → 未完成的整備，每筆附上車輛（車牌、車款）與該車「下一次取車」
POST /prep-tasks/{id}/complete       → 記錄 completedAt（伺服器時間）與 completedBy（登入身分），回傳更新後的整筆
```

- **下一次取車**＝該車尚未取車（reserved）的訂單中取車時間最早的一筆；**取車時間已過但還沒取車的也算**（客人在等車，是最急的情況）。
- **排序**：依下一次取車時間由近到遠，沒有下一筆的排最後；相同時先還車的排前面。
- 總覽頁首徽章要「未完成的整備數」，可由同一支 API 的筆數得到，或另給計數。
- 取車清單的「尚未整備」提醒只需要知道「這台車有沒有未完成的整備」；若取車清單改由後端提供，請在每一列附上這個布林值。

### 8.4 後端驗收情境

1. 還車完成後出現一筆未完成的整備，車輛、訂單、實際還車時間、還車據點正確；車輛狀態仍是可出租、可用數不變。
2. 按整備完成後從未完成清單消失，完成時間與操作人有記錄；重複送出不改寫第一次的紀錄。
3. 同一台車未整備就再次還車：舊的一筆標記為被取代（不是完成），未完成清單中這台車只剩新的一筆。
4. 未完成清單依下一次取車時間排序，取車時間已過但未取車的預訂排在最前，沒有下一筆的排最後。
5. 有未完成整備的車仍可正常取車，取車就緒判斷不出現與整備有關的阻擋。

## 9. 建單時一併寫入的證件與駕駛資格（2026-09-24 追加，後台流程審查 4.1、4.2）

批次 4.2 把駕駛資格（駕照號碼、效期、准駕類別、外國旅客互惠查核）從會員視窗搬進建立訂單頁第 2 步，建立訂單時會與承租人證件一起寫入，不再只能靠事後開會員視窗補。後端把「建立訂單」做成一個交易或 saga（見第 1.3 節）時，這兩筆證件寫入要跟會員、訂單、款項、合約算在同一個原子操作裡。

### 9.1 承租人證件與駕駛資格何時寫入

前端實作在 `apps/admin/src/app/features/orders/data/admin-order-submit.gateway.ts` 的 `recordDocuments()`（送出序列第 6 步，介於「合約」與「排程還車提醒」之間）：

- **身分證明文件**：只有「這次新建的承租人」（既有會員的證件欄位鎖定、不重新核對）且填了證件號碼，才建立一筆 `IdentityDocument`，型別依 `requiredIdentityDocumentType(kind)`（本國人→`taiwan_id`、外國旅客→`passport`、持居留證者→`resident_permit`），建立後立即以目前登入的後台使用者標記為 `verified`（現場人員當場核對）。
- **駕駛資格**：填了駕照號碼才建立 `DriverCredential`；標準化車種（`standardizedVehicleClass`）必填，缺漏會被表單驗證擋在送出前，gateway 端也再擋一次（寧可整筆送出失敗）。若與這位會員「目前最新一版」內容相同（`sameDriverCredential()`），沿用既有那筆、不重複建立，查核狀態也一併沿用。外國旅客的駕駛資格建立後立即觸發互惠資格查核（`checkDriverEligibility()`）；查核本身失敗不擋建立訂單，只會留下「駕駛資格未查核」的待補項目（見第 9.3 節、第 9.4 節）。
- 編輯既有訂單（`update()`）不會呼叫 `recordDocuments()`——第 2 步的駕駛資格區塊只在建立訂單頁出現，編輯表單沒有這兩個欄位群，既有會員的證件只能經會員視窗另外改。
- 建立失敗時的補償範圍包含這次新建的證件／駕駛資格紀錄；沿用既有版本的舊紀錄不會被補償刪除。

### 9.2 證件版本規則：新版本追加，不覆寫

`IdentityDocument`／`DriverCredential`（`libs/domain/src/lib/models/identity-document.ts`）都以「新版本追加」的方式更新，不覆寫舊版：新版本 `version = 前一版.version + 1`（沒有前一版就是 1），並寫 `supersededId` 指回前一版的 id（第一版沒有這個欄位）。實作在 `apps/admin/src/app/stores/document/document.store.ts` 的 `uploadIdentityDocument()`／`uploadDriverCredential()`。

這是這批順手修的一個既有 bug：改之前每次上傳都固定寫 `version: 1`，交車檢查「取最新版本」的邏輯因此一直拿到最舊那筆，客人換了新駕照、上傳更新版本後，取車當場的檢查仍看到舊駕照。後端儲存這兩種證件時請比照：更新一律插入新版本、`supersededId` 指回前一版；「目前有效版本」＝同一 `memberId`＋同一種類（`type`）裡 `version` 最大的那筆，不要用 `updatedAt` 排序或直接覆寫既有列來實作。

### 9.3 待補項目規則的現在位置（更正第 5 節的舊路徑）

第 5 節原本寫的 `orderIncompleteItems` 位置已過時，現況：整套「待補項目」規則收在 `apps/admin/src/app/features/orders/incomplete/order-incomplete.ts`，建立訂單頁摘要欄、訂單詳情、訂單列表三處共用同一份判斷：

- 兩種資料來源先各自整理成同一份 `OrderIncompleteFacts`：`incompleteFactsFromForm()`（建單頁，吃表單目前的值）、`incompleteFactsFromOrder()`（訂單詳情／列表，吃已成立訂單的實際紀錄——款項、合約版本、承租人的證件與駕駛資格）。
- 兩者都交給同一個 `orderIncompleteKinds(facts)` 判斷本體，保證同樣的情況在建單頁與訂單詳情、列表一定列出同樣的項目；`orderIncompleteItems(facts)` 是外層再包成畫面用的清單（含文字與可點的分頁／對象）。
- 批次 4.1/4.2 新增兩個項目：`證件未查核`（承租人身分別要求的證件缺席，或有紀錄但還沒核對完成）與`駕駛資格未查核`（駕照缺席、未核對，或外國旅客的互惠查核結果不是「符合」）。

後端若要在伺服器端提供同一份「待補項目」資訊（例如給前端直接讀、取代前端自己算），請照 `order-incomplete.ts` 這套規則實作，不要另外定義一套判斷——`駕駛資格未查核` 用的「目前有效版本」概念與交車前檢查（第 2.2 節）是同一件事，兩處標準不一致會出現「待補清單說沒問題、交車卻被擋」的落差。

### 9.4 外國旅客互惠查核目前是開發用模擬

`checkDriverEligibility()` 呼叫的 `DriverEligibilityGateway`（`apps/admin/src/app/core/services/driver-eligibility.gateway.ts`）目前只有一個假實作 `MockDriverEligibilityGateway`：沒有串接任何真正的外國駕照互惠清單，除非測試／展示明確呼叫 `setFixture()` 掛規則，一律回傳 `reciprocityStatus: 'manual_review'`（需人工審查）。後端接手時這裡需要真正的資料源（互惠國家清單、駕照類型對應規則），介面可沿用 `checkReciprocity({ issuingCountry, credentialType })` 這個形狀，回傳 `reciprocityStatus`（與可能的 `legalUseThroughDate`）。
